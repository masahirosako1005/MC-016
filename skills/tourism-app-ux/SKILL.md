# 観光アプリの UI/UX の型

観光スタンプラリーに足すスマホ Web アプリ「ひとめぐり」を、10 回のフィードバックで磨いた経験から取り出した型。
目的は、**次に似たアプリを作るとき、利用者が細かく指示しなくても同じ水準の UI/UX に最初から届くこと**。

ここに書くのは規則ではなく「なぜそうしたか」つきの判断の型。題材が違えば色も言葉も変わるので、理由を読んで応用する。
見本の色（藍と山吹）や言葉（会えた・ひとめぐり帖）、部品の見た目をそのまま写さない。写すのは考え方。出来上がりが見本の色ちがいに見えたら、題材らしさが足りていない。

## まず決めること（作り始める前）

画面を作る前に、まず配色を決め、そのあと次の 5 つを 1〜2 行ずつ書き出す。ここが曖昧だと、あとで画面を全部作り直すことになる（実際にそうなった）。

### 最初に配色を決める（4 色）

コードを書く前に、次の 4 色を色名と値で決めて、設計メモの先頭に書く。画面の印象の大半はここで決まる。

| 役割 | 決め方 | 見本（ひとめぐり） |
|---|---|---|
| **テーマ色** | 題材に実際にあるものから拾った色。ひと目で「何色」と言える色にする（黒や灰色に見える色は選ばない） | 藍 `#1b2a44` |
| **強調色** | テーマ色と並べたときにはっきり映える色。寒色のテーマには暖色、暗いテーマには明るい色 | 山吹 `#e3a21a` |
| **背景の色** | テーマ色をごくわずかに混ぜた、紙のような明るい色 | 紙 `#fbfcfd` |
| **字の色** | テーマ色そのもの、またはそれをさらに濃くした色。背景の上で十分読める濃さ | 藍 `#1b2a44` |

色は思いつきで決めず、**題材に実際にあるもの（のれん、屋根、名産、土地の花など）を 5 つほど挙げ、その色から選ぶ**。見本やこの Skill に出てくる組み合わせをそのまま使わない。
決めたら、**テーマ色と強調色を隣に並べて見る**。藍と山吹のように、互いを引き立てる組み合わせになっていなければ選び直す。
強調色が弱い・テーマ色が黒に近いと、画面全体がのっぺりする（実際に、墨茶 1 色で作った版がそうなった）。
詳しい手順は `references/visual-design.md` の「2. 色の決め方」。

### そのあと決める 5 つ

1. **開く理由**: 利用者がこのアプリを開く理由を、場面ごとに 1 つずつ。観光なら「行く前／その場／帰ったあと」。場面が 1 つしかないアプリは、その場面が終わると開かれなくなる。
2. **入口**: 利用者がもともと探しているもの（観光なら「場所」）。アプリが足したい新しい価値（人との出会い、など）は入口にしない。入口の中に付加情報として置く。
3. **見せる概念は 1 つ**: 利用者に覚えてもらう独自の概念（進み具合・関係・ランクなど）は 1 つに絞る。2 つ目を足したくなったら、データだけ持って画面には出さない。
4. **世界観**: 題材から連想できる素材を 1 つ選ぶ（例: 藍染と和紙の手紙）。書体・言葉づかい・小さな飾り・絵の描き方をそこから決める。その題材にしかない見せ方を 1 つ入れる（温泉なら湯めぐり手形、島なら航路、など）。
5. **作らないもの**: 格付け・星・ランキングなど、題材の趣旨に反するもの。先に書いておくと、集計画面を作るときに迷わない。

利用者に確認が必要なのは 1・2・5 だけ。配色と 3・4 は提案して進めてよい。

## 進め方

1. **最初に通しで動かす**。全場面を最小限でつなぎ、最初から最後まで 1 回通せる状態を先に作る。1 画面を磨くのはそのあと。
2. **画面は「型」から組む**。下の「画面の型」と `assets/` の見本をそのまま土台にする。
3. **ブラウザで実際に触って確かめる**。スマホ幅（375px）で、主な流れを最初から最後まで操作する。見た目だけでなく、スクロールせずに主ボタンに届くかを見る。
4. **完成前に `references/review-checklist.md` を通す**。
5. **フィードバックは 1 件ずつ「原因の型」に戻す**。言われた箇所だけ直すのではなく、同じ原因の箇所をほかの画面でも直す（`references/lessons-from-feedback.md` に実例）。

進行の約束ごと（質問の扱い・判断の記録・デモ用の層・削る順番）は `references/process.md`。長い作業や発表つきの案件では最初に読む。

## 画面の型（要点）

詳しい理由と実例は `references/ux-patterns.md`。ここは忘れると必ず指摘される項目だけ。

- **各タブの一番上に「いまやること」カード**。文 1 つと主ボタン 1 つ。利用者の状態（旅前・旅中・旅後、未入力・完了）から組み立てる。画面を開いた人が「で、何をすれば？」と迷わない。
- **主ボタンは 1 画面に 1 つ**。塗りつぶしは 1 つだけ、ほかは枠線か文字。
- **下タブは目的ごとに 1 つ、利用者の言葉で名づける**。5 つまで。1 つのタブに 2 つの目的を切替で押し込まない。
- **隠れた操作を使わない**。長押し・ダブルタップ・スワイプだけの操作は気づかれない。スワイプには必ず同じ働きのボタンを添える。大事な操作は「ボタン → 確認」。
- **主な操作はスクロールなしで届く位置に**。カメラならシャッターは映像のすぐ下に大きく 1 つ、選択肢はその下に横スクロール。記録の画面なら、絵のすぐ下に主ボタン、任意の入力（写真・ひとこと）はその下。任意の入力を主ボタンより上に置かない。
- **同じ情報を 1 画面に 2 回出さない**。「いまやること」に出した内容を、下の固定バーや別のカードでもう一度出さない。どちらか 1 か所に決める。
- **固定の部品で中身を隠さない**。下に固定するバーやポップアップは、一覧の最後の行や、いま選んでいるものに重ならないようにする（下に余白を足す、重なるなら位置を変える）。
- **結果は、操作した場所のすぐ下に出す**。「撮る」ボタンの下に撮った写真、「レシートを撮る」の下に登録した一覧。別の画面に探しに行かせない。
- **画面の移動を減らす**。一覧や地図の項目は、まずその場のポップアップで要点を見せ、操作もその中で。詳しく見たい人だけが次の画面へ。
- **同じ種類の操作は同じ配置**。撮影が 2 か所あるなら、ボタンの位置・大きさ・流れをそろえる。
- **操作できる場面を絞る**。ふり返りの画面からはボタンを外して見るだけにする。その操作が意味を持つ場面でだけ押せるようにし、ほかの場面からはそこへ案内する。
- **入力を減らす**。妥当な初期値を入れておく（名前は「○○旅行 N 回目」など）。読み取った値は入れておき、利用者は確認だけ。
- **「なぜ今これか」を一言のタグで添える**。おすすめには理由（「前回行けなかった場所」「春に行った → 秋はどう？」）。順位や点数では示さない。
- **選んだ時点で「回りきれるか」を見せる**。行きたい場所を選ぶと、数と所要時間の目安（「外湯 3・お店 2／およそ 2 時間 20 分」）がその場に出る。
- **集めるものは、空き枠ごと見せる**。まだの枠を点線で残し、「あと 5 つ」と一言添える。残りが目に見えることが、また来たい気持ちにつながる。
- **場所は名前を読まなくても見分けられるように**。場所ごとに一文字・紋・色のちがう絵を割り当て、一覧・地図・記録で同じものを使う。
- **動きは意味のある瞬間だけ**。達成・結果・届いたとき。常時動くもの（点滅する現在地など）は入れない。
- **初回は 3 枚のガイド＋画面ごとに 1 度だけの図解**。「？」でいつでも出し直せる。
- **使えないときの逃げ道を用意**。カメラ不可 → 写真を選ぶ → 用意した絵、のように必ず最後まで進めるようにする。

## 見た目の型（要点）

詳しくは `references/visual-design.md`。土台は `assets/tokens.css` と `assets/base.css` をコピーして、色の値だけ差し替える。

- **部品の色は、最初に決めた 4 色だけ**。テーマ色の濃淡 6 段階で画面の大部分を作り、状態（選択中・済み・無効）も濃淡で表す。3 色目・4 色目を部品に足さない。
- **強調色は、どの画面でもはっきり見える**。進み具合の棒、地図の「行く」ピン、達成の印や帯、選択中の下線、数の札、主ボタンの印など、「見てほしいところ」に使う。小さな点だけで終わらせない。1 画面に 1〜3 箇所、合わせて画面の 1 割ほど。本文の文字色と広い面には使わない。
- **絵は色の決まりの外**。場所の絵・地図・キャラクター・写真は、場所ごとに色を変えて豊かに描く。ただしテーマ色と強調色を絵の中にも入れて、画面となじませる。絵まで単色にすると地味になる。
- **最初の画面で世界観が伝わる**。題字まわりや先頭のカードに、題材の絵か飾りを小さく入れる。ただし先頭の領域は「いまやること」が主役で、飾りに画面の半分を使わない。
- **地は紙の色（真っ白にしない）、カードは白**。枠線はテーマ色のいちばん薄い段階。影はほぼ使わない。
- **見出しは明朝、本文はゴシック**（どちらも OS に入っている書体。外部フォントは読み込まない）。
- **角丸 8px、押せるものは高さ 48px 以上、本文 16px**。文字の大きさは設定で 3 段階に変えられるよう、rem で組む。
- **お知らせ（トースト）は控えめに**。濃い色の帯ではなく、半透明の紙に薄いテーマ色の文字、短い 1 文。
- **絵は自前で、場所ごとに描き分ける**。アイコン・図解・地図の上の印は SVG で描く。場所の絵は記号 1 つで済ませず、その場所の特徴（川べり、石段、月、湯けむり）が分かる小さな風景にする。写真や素材を借りたら出典を 1 つの文書にまとめる。
- **キャラクターを置くなら、役割を持たせる**。「いまやること」・読み込み中・空の状態・お礼など、文字だけだと冷たくなる場所に小さく。

## 運営者向けの画面があるとき

`references/ux-patterns.md` の「運営の画面」を読む。要点だけ:

- 開いたら毎回ホーム。ホームの先頭は数字ではなく **「次の一手」**（データから組み立てた提案と、そこへ飛ぶボタン）。
- 立場（地域全体／個々の店）で機能を分ける。立場は権限で決まるものなので、画面上部に切替を置かない。
- 説明文は消す。見出しと数字と操作だけ。スマホ幅では 1 列。
- **順位をつけない**。比べるなら平均と比べる。少人数（3 件未満）は集計を出さない。利用者は ID ではなく呼び名で出す。

## 同梱ファイル

| ファイル | 読む・使う場面 |
|---|---|
| `references/ux-patterns.md` | 画面構成を決めるとき。型ごとの理由と実例 |
| `references/visual-design.md` | 色・書体・部品の見た目を決めるとき |
| `references/lessons-from-feedback.md` | フィードバックを受けたとき、または仕上げ前に「指摘されそうな点」を先に潰すとき |
| `references/process.md` | 作業の進め方、判断の記録、デモ・発表用の作り |
| `references/review-checklist.md` | 完成と言う前に必ず通す |
| `assets/tokens.css` | 色・書体・寸法の変数。値を差し替えて使う |
| `assets/base.css` | 部品の CSS（いまやること・ボタン・カード・下タブ・トースト・ガイド・ポップアップほか） |
| `assets/components.tsx` | React の部品見本（ライブラリなし。いまやること・手順帯・初回ガイド・トースト・下タブ・ハッシュルーター） |

`assets/` は React + 素の CSS を前提にした見本。別の構成（Vue、Tailwind など）なら、クラス名や書き方は合わせ直し、寸法・色の使い方・部品の構造だけを引き継ぐ。
