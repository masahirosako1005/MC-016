# フィードバックから得た教訓

「ひとめぐり」は 10 回のフィードバックで作り直した。ここにあるのは、**最初の版でやってしまい、指摘されて直したこと**。
つまり、何も言われなければまた同じことをやる可能性が高い項目。仕上げる前にここを読み、先に潰しておく。

各項目は「最初にやったこと → 指摘 → 直し方 → 取り出した型」。

## 構成

### 1. 新しい概念を入口にした
- 最初: 「会える人」を入口にし、スタンプラリーの要素（行けた・スポット撮影）も並べた。
- 指摘: 何のアプリか分からない。人を選んだつもりがないのに会いに行く流れになる。
- 直し: 入口を「場所」に戻し、人は「ここにいる人」として添えた。スタンプラリーの要素は外した。
- 型: **入口は利用者がもともと探しているもの。足したい価値は中に添える。既存の仕組みの要素を惰性で残さない。**

### 2. タブを節約して 1 つに 2 つ押し込んだ
- 最初: タブ 4 つを保つため、「思い出」タブの中に切替で 2 画面を入れた。
- 直し: タブを 5 つにして独立させた。
- 型: **目的が別ならタブを分ける。数を守るために目的を混ぜない。**

### 3. 概念を重ねすぎた
- 最初: 種 → つぼみ → 花、季節のスタンプ 32 個、回数の帯、を同時に見せた。
- 指摘: どれを見ればいいのか分からない。
- 直し: 見せるのは「会えた回数」の帯 3 段階だけ。種と花は画面から外し、データと API は残した。
- 型: **利用者に見せる物差しは 1 つ。作り込んだ仕組みでも、画面から外す判断をためらわない。**

## 操作

### 4. 長押しを使った
- 最初: 大事な操作（約束を果たす・クーポンを使う）を「1.2 秒の長押し」にした。誤操作を防ぐつもりだった。
- 指摘: 押し方が分からない。
- 直し: 全廃。「ボタン → 確認」に統一。
- 型: **隠れた操作は気づかれない。誤操作は確認で防ぐ。**

### 5. ピンを直接押すと状態が変わった
- 最初: 地図のピンをタップすると「行く／行かない」が切り替わった。
- 直し: タップでポップアップを出し、その中のボタンで切り替える。
- 型: **タップで起きるのは「見る」まで。状態を変えるのは名前のついたボタン。**

### 6. 主な操作がスクロールの下にあった
- 最初: カメラの画面で、映像 → フレーム選択 → シャッターの順に縦に並べた。
- 直し: シャッターを映像の直下に大きく 1 つ。フレームはその下に横スクロール。
- 型: **その画面でいちばんやることは、開いた瞬間に指が届く位置に。**

### 7. 同じ種類の操作なのに作りが違った
- 最初: AR フォトは専用画面、レシート撮影は場所の画面の中に埋め込み、ボタン配置も別。
- 直し: レシートも専用画面にし、カメラ → 「撮る」→ 確認 → もどる、の流れと配置をそろえた。
- 型: **同じ種類の操作は、同じ場所・同じ流れ。**

### 8. 結果が別の画面に行っていた
- 最初: 撮った写真はアルバム、レシートはクーポンのタブにしか出なかった。
- 直し: 「撮る」ボタンの直下に新しい 3 枚、「レシートを撮る」の直下に表（新しい 5 件 + 合計）。
- 型: **結果は、操作した場所のすぐ下に出す。**

### 9. どこでも操作できるようにした
- 最初: 人の詳細画面にも「会えた」ボタンを置いた。ふり返りの画面から開いても押せた。
- 直し: 「会えた」は旅の途中、場所の画面でだけ。ふり返りから開いた画面は見るだけ。
- 型: **操作は意味を持つ場面でだけ。ほかからはそこへ案内する。**

### 10. 入力の場所が分かりにくかった
- 最初 → 2 回目: 入力欄 → 付箋に直接書く → やはり入力欄、と往復した。
- 型: **見た目の比喩（付箋）と入力のしやすさがぶつかったら、入力は素直な入力欄に。比喩は表示側で使う。**

## 見た目と動き

### 11. お知らせが強すぎた
- 最初: 濃い紺の帯に白文字のトースト。
- 直し: 半透明の紙に薄い藍の文字、短く。
- 型: **お知らせは内容より目立ってはいけない。**

### 12. 常時動くものを入れた
- 最初: 現在地の点が波紋のように動き続けた。
- 直し: 削除。
- 型: **動きは意味のある瞬間だけ。**

### 13. 演出がまわりを揺らした
- 最初: 回るルーレット（四角い SVG）の角がはみ出し、回転のたびに下タブが揺れた。
- 直し: 丸い箱（`overflow: hidden` と `contain: layout paint`）に閉じ込めた。
- 型: **回転・拡大するものは箱に閉じ込める。演出を入れたら、まわりの部品が動いていないか見る。**

### 14. 演出の見た目から確率が読めた
- 最初: ルーレットのマスの広さを確率に比例させた。その前はスロット（3 つそろうかのように見える）。
- 直し: マスは同じ広さで当たり・はずれを交互に。確率は折りたたみの表で見せる。結果は API が先に決める。
- 型: **演出は結果を伝えるだけ。確率は演出ではなく表で、正直に。**

### 15. めくったカードが戻ってきた
- 最初: カードをめくると、同じ要素が使い回されて上に「戻ってくる」動きになった。
- 直し: key を項目の ID にし、下のカードが見えている「積み重ね」にした。
- 型: **並びが変わるリストの key は ID。動きを付けたら、連続で操作して確かめる。**

### 16. 丸いチップを何にでも使った
- 最初: 運営の画面の機能切替を丸いチップの列にした。
- 直し: 立場の大きなタブ → 下線つきの機能タブ → いまの場所表示。
- 型: **チップは「選ぶ・絞る」、タブは「移る」。役割で形を分ける。**

## 運営の画面

### 17. 説明文を書きすぎた
- 最初: 見出しの下、指標の横、タブの下に説明文を付けた。
- 直し: すべて削除。
- 型: **説明が要る画面は、説明を足すのではなく画面を直す。**

### 18. 立場の切替を目立つ場所に置いた
- 最初: 画面上部に「DMO／お店」の切替。
- 指摘: 本番では権限で決まるもの。
- 直し: デモ用の小さな設定ボタン（右下）と発表画面の操作列に移した。
- 型: **デモの都合で必要な操作を、本番の画面の一等地に置かない。**

### 19. 数字から始めた
- 最初: 開くと指標の一覧。
- 直し: 開くたびにホーム、先頭は「次の一手」（提案と、そこへ飛ぶボタン）。
- 型: **運営者が知りたいのは数字ではなく、次に何をすればいいか。**

### 20. ID をそのまま出した
- 最初: 「会ったことのある旅行者」を ID と機械的な名前で表示。
- 直し: 呼び名で表示（年代・地域があれば添える）。
- 型: **人は人として見せる。**

### 21. 集計がそのまま格付けになりかけた
- アンケートを足したとき、店ごとの満足度の平均を出せば実質的に星レビューになる。
- 直し: 平均と分布は全体でだけ。店には自分の場所への声（タグ件数と文章）だけ。タグは定義順。3 件未満は出さない。
- 型: **「作らないもの」は、機能を足すたびに照らし直す。**

## 文言・名前

### 22. 内部の呼び名が画面に出ていた
- 「10/24 の便」→「10/24 の思い出」。人の名前は下の名前の呼び捨てふう →「苗字 + さん」。
- 型: **画面の言葉は、利用者が声に出して言える形に。**

### 23. 名前を変えたら古い名前が残った
- アプリ名や人の名前を変えたとき、既存データの文章・書き出した画像・ブラウザのキャッシュに旧名が残った。
- 直し: 起動時に既存データを置き換え（何度実行しても同じ結果。利用者が書いた文章は触らない）。画面の入口（index.html）は `Cache-Control: no-cache`。
- 型: **名前の変更は、マスタ・既存データ・画像・キャッシュの 4 か所を見る。**

## デモ・発表

### 24. デモの初期化が不完全だった
- やり直すたびに、前回の回答・送った便り・既読が残っていて、見せたい画面が出なかった。
- 型: **初期化は「主人公が作ったもの全部」を消す。機能を足したら初期化にも足す。**

### 25. デモで見せたい演出が運まかせだった
- 抽選の「会った人が渡してくれる」演出が、はずれると見せられない。
- 直し: デモのときだけ最初の 1 回は必ず当たる。本番では分岐に入らないことをテストで確認。
- 型: **デモ用の分岐は、本番に影響しないことをテストで保証する。**

### 26. 発表画面の説明と操作がずれた
- 直し: 場面ボタンとスライドを 1 対 1 に。箇条書きをやめ、短い見出し + 説明 1 行 + ねらい 1 行。
- 型: **横に置く説明は「いま何を見せているか」だけ。**

## 比較試験から（Skill あり／なしで同じアプリを作らせた結果）

この Skill の版 0.1 を使って作らせたアプリと、Skill なしで作らせたアプリを比べて分かったこと。

### 27. 色を絞りすぎて、のっぺりした
- 起きたこと: テーマ色に黒に近い茶を選び、強調色は小さな点にしか使わなかった。整ってはいるが、画面全体が無彩色で地味になった。
- 元のアプリで良かったのは、藍と山吹がはっきり対比していたこと。
- 型: **最初に 4 色（テーマ色・強調色・背景・字）を決める。テーマ色は色名で呼べる色に、強調色はどの画面でも目に入る大きさで使う。**

### 28. 絵まで単色になった
- 起きたこと: 「色を足さない」を場所の絵にも当てはめ、記号 1 つの単色の絵になった。Skill なしの版は、場所ごとに色のちがう風景を描いていて、ぱっと見の魅力で上回った。
- 型: **色の決まりは部品のもの。絵・地図・キャラクターは豊かに描き、場所ごとに描き分ける。**

### 29. 見本の色ちがいになった
- 起きたこと: 構成も部品の見た目も、元のアプリとほぼ同じになった。使いやすさは保てたが、題材らしさが薄い。
- 型: **型は骨組み。題材にしかない見せ方を 1 つ入れ、最初の画面で世界観が伝わるようにする。**

### 30. Skill なしの版にあって、こちらになかった工夫
- 計画の時点で所要時間の目安を出す（「およそ 2 時間 23 分」）
- 集める枠を点線の空き枠ごと見せ、「あと 5 つ」と添える
- 地図のピンを漢字一文字にして、名前を読まずに見分けられるようにする
- 型: **比べて負けた点は、そのまま型に取り込む。**

### 31. 例示した配色を、そのまま使った
- 起きたこと: 版 0.2 に「この題材ならこの 2 色」という例を題材別に書いたところ、その組み合わせがそのまま使われた。
- 型: **答えの例を並べると写される。例は見本 1 つにとどめ、決め方（題材の実物から色を拾う）を書く。**

### 32. 取り込んだ工夫が、二重表示と重なりを生んだ
- 起きたこと: 所要時間を「いまやること」と下の固定バーの両方に出し、固定バーが一覧に重なった。地図のポップアップが下側のピンを隠した。記録画面では、任意の入力が主ボタンより上に入り、主ボタンが下がった。
- 型: **足したら、同じ情報が 2 か所にないか、固定の部品が中身を隠していないか、主ボタンが下がっていないかを見直す。**
