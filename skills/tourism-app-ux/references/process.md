# 進め方

UI/UX の質は、画面の作り方だけでなく進め方で決まった部分が大きい。うまくいったやり方を残す。

## 1. 最初に仕様を固め、あとは止まらない

- **作り始める前にだけ、まとめて質問する**。目的・場面・作らないもの・技術の制約を、数往復で決め切る。
- **決まったあとは質問で止まらない**。迷ったら妥当な方を選び、選んだ理由を記録して進む。利用者があとから見て、違えばそこだけ直せる。
- 利用者が「質問しないで進めて」と言っている場合、途中で使う道具や手順が確認を求めてきても、その約束を優先する。

## 2. 記録を 3 つ持つ

| 文書 | 中身 | 書き方 |
|---|---|---|
| プロジェクト要約（`CLAUDE.md`） | 目的・約束・画面・ルール・技術。次の作業者が最初に読む 1 枚 | 仕様が変わったらその場で書き換える。履歴は書かない |
| 判断の記録（例: `docs/00_requirements.md`） | 迷った点と選んだ方、その理由 | 日付つきで 1 件 1〜数行。追記のみ |
| 進捗（例: `docs/10_progress.md`） | やったこと、確認の結果、できなかったこと | 時刻つき 1 行。テスト件数も書く |

判断の記録には **「何をやめたか」と「なぜ」** を必ず書く。あとで同じ案が出たときに往復しない。
できなかったこと・確かめていないこと（実機のカメラ、実際の印刷など）も進捗に正直に書く。

## 3. 削る順番を先に決める

時間が足りなくなったときに削る順を、最初に並べておく。**通しで動くことが最優先**。

例（観光アプリ）: やさしい日本語 → 印刷レイアウト → 傾きの視差 → 絵の地図 → 一覧画面 → 確率の表示 → 設定の変更 → 抽選。

順番があると、途中で迷わず削れ、利用者にも説明できる。

## 4. 作る順番

1. **土台**: データの形、時刻の取得口、エラーの形、起動の手順。
2. **通し**: 全場面を最小限でつなぐ。見た目は後。
3. **見た目と構成の作り直し**: ここで初めて世界観・タブ・「いまやること」を入れる。通しで触った感触から決める。
4. **フィードバックの反映**: 1 回ごとに、指摘を一覧にする → 直す → 判断を記録 → 通しで確かめる。
5. **自己点検**: 複数の観点（機能・画面・データ・安全・テスト・文書・デモ・ライセンスなど）で見直し、要修正を直す。

毎回の区切りで、テストとビルドを通し、ブラウザで主な流れを触る。

## 5. フィードバックの受け方

- 指摘は言葉どおりに直すだけでなく、**同じ原因の箇所をほかの画面でも直す**（「レシート撮影のボタン位置を AR とそろえて」→ 撮影系すべての配置をそろえる）。
- 直した結果、前の判断を取り消すことになったら、取り消しも記録する（「長押しを全廃」「付箋への直接入力をやめて入力欄に戻した」）。
- 画面から外すと決めた機能は、**データと API を残す**。画面からの呼び出しだけ外す。
- 仕様の数字（しきい値、単価）が変わったら、プロジェクト要約・判断の記録・テストを同時に直す。

## 6. 時刻は 1 か所から

「きょう」「いまの季節」「30 日後」など、時刻で画面が変わるアプリは、時刻を取る場所を 1 つにまとめる（clock サービス）。
画面の提案や集計が実時刻を直接見ていると、デモや試験で食い違う（実際に 1 件あった）。

## 7. 本体とデモ用の層を分ける

発表やデモがある案件では、最初から分ける。

- 本体はふつうに動く。デモ用の API と発表画面は、起動時の設定（例: `DEMO_MODE=1`）があるときだけ有効。設定がなければ 404 を返すことをテストで確かめる。
- **デモ時計**: 場面ごとの日時（行く前 → 当日 → その夜 → 30 日後 → 次の季節）をボタン 1 つで切り替える。
- **初期化**: 主人公が作ったものをすべて消して最初に戻す。機能を足すたびに初期化にも足す。
- **デモだけの分岐**（必ず当たる抽選など）は、本番では入らないことをテストで確かめる。
- **発表画面**: 左にスマホ枠で本体（iframe）、右に場面の説明。場面ボタンと説明を 1 対 1 に。説明は短い見出し + 1 行 + ねらい 1 行。操作列（前／次・初期化）は下に 1 段。
- デモの都合の操作（立場の切替など）は、本体の画面の目立つ場所に置かず、隅の小さな設定に入れる。

## 8. 技術の選び方（UI の質に関わる点）

- **外部の読み込みをなくす**。CDN・外部フォント・外部地図を使わず、絵は自前の SVG、素材は自分のサーバーから配る。表示が速く、会場の通信に左右されない。
- **小さな構成**。画面のライブラリを最小にし（ルーターは URL のハッシュで自作、UI ライブラリなし）、色と部品は CSS 変数と素の CSS で持つ。世界観をすみずみまで揃えやすい。
- **画面とサーバーを同じ場所から配る**。ビルドした画面をサーバーが配信すれば、起動が 1 つで済む。
- **画面の入口はキャッシュさせない**（`Cache-Control: no-cache`）。作り直しても古い画面が出続ける事故を防ぐ。
- **設定は端末に保存**（文字の大きさ・配色・やさしい日本語）。保存できない環境でも動くようにする。

## 9. 自己点検で実際に見つかったもの

仕上げの点検で見つかり、利用者の画面に影響した例。同じものを先に確かめる。

- 画面を配る処理で、URL を細工するとサーバー内の別のファイルが取れた（配る範囲をビルド結果の中に限定して修正）
- 運営の編集で、送っていない項目まで空で上書きされた（送られた項目だけ更新するよう修正）
- 入力の検証漏れ（営業時間 `99:99`）で、利用者の画面がエラーになった
- 再起動すると運営の編集内容が初期値に戻った（起動時の更新対象から編集できる列を外して修正）
- キーボード操作、フォーカスの扱い、動きを減らす設定への対応が抜けていた
